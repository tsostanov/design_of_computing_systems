# Проверки ЛР №2

## Выполненные программные проверки

Полная чистая сборка выполнена STM32CubeIDE 1.9.0 через headless build. Среда заново сформировала make-файлы и включила новые модули и HAL UART. Результат: **0 ошибок, 0 предупреждений**.

В этой Debug-сборке: text=20924, data=120, bss=4160 байт. Значения могут измениться после доработки или смены оптимизации.

`python tests/run_tests.py` компилирует настоящие C-файлы GCC с `-Wall -Wextra -Werror`, запускает их, затем Python unittest.

| Группа | Проверки |
|---|---|
| C: ring | Пустая/полная очередь, все ячейки доступны, отказ записи целого блока, 1000 оборотов, FIFO |
| C: codec | Все A–Z по эталонной таблице, нижний регистр, неизвестные последовательности |
| C: morse | 8 ожидающих + текущая, отказ лишней, границы импульсов/пауз, одновременный ввод, переполнение ввода и времени |
| C: button | Дребезг, устойчивое нажатие/отпускание, короткое/длинное событие, переполнение времени |
| C: uart | HAL_TIMEOUT после записи без дублирования, IT↔polling, незавершённый TX, сохранённый RX, переполнение, ошибки и восстановление |
| C: app | Точные байты протокола, CR/LF, неизвестный символ, переключение, кнопка во время передачи |
| Python: 11 тестов | Таблица и настройки, очередь/время/ошибки, частичная запись, точное сравнение протокола с C-приложением, обработчики и цвета окна |

Имитация HAL не моделирует физические сигналы и все гонки периферии. Она позволяет контролировать TC и завершение байта, но не измерять потери реального UART на 115200.

Tkinter проверялся программно: создание виджетов, обработка событий, проверка цветов. Это не проверка обмена PuTTY через настоящую COM-пару.

## Сценарии на стенде

Подключить стенд, собрать и запустить прошивку, настроить PuTTY по README. Выполнить сценарии сначала с прерываниями. Нажать `+`, дождаться `interrupts off` и повторить в опросе.

| № | Действия | Ожидаемый результат |
|---|---|---|
| 1 | Отправить E, после окончания T | Эхо, transmitting symbol; импульсы около 200 и 600 мс |
| 2 | Отправить a | Эхо a, сообщение с A, точка–тире |
| 3 | Быстро отправить ABC | Три сообщения о принятии, проигрывание A, B, C |
| 4 | Во время передачи A отправить B | A не прерывается, затем проигрывается B |
| 5 | Отправить TTTT, во время мигания кнопкой ввести точку–тире | Мигание продолжается; после паузы — received symbol: A |
| 6 | Удерживать кнопку более 5 с, одновременно отправлять буквы | UART и мигание работают; результат кнопки только после отпускания и паузы |
| 7 | Быстрой вставкой отправить EEEEEEEEEE | Если всё пришло до окончания первой E, приняты 9 букв, десятая отклонена |
| 8 | Плюс в простое, затем во время мигания | Новый режим указан; буква, очередь и ввод сохранены |
| 9 | A с Enter; отдельно вопросительный знак | Нет ошибки на CR/LF, есть ошибка на вопросительный знак; эхо не удвоено |
| 10 | Кнопкой пять точек | error: invalid morse sequence; затем можно ввести новую букву |
| 11 | Кнопкой девять знаков, промежутки меньше 2 с | error: morse input overflow; усечённая буква не выдаётся |
| 12 | Большая пачка символов, затем остановка ввода | Возможен rx_overflow; после освобождения очередей обычный ввод работает |
| 13 | В потоке отправлять плюсы, затем проверить букву и кнопку | Нет зависания; отдельно записать потери и счётчики ошибок |

В №7 между буквами не нужно ждать: при освобождении мест десятая буква может законно быть принята. В №12–13 непрерывный поток не обязан пройти без потерь: длинные ответы и вход используют один baud rate, буферы ограничены.

Для измерения импульсов и участков маскирования IRQ нужен осциллограф/логический анализатор. Визуальная проверка подтверждает порядок, но не точность до миллисекунды.

## Проверка симулятора через COM-пару

1. Создать COM10 ↔ COM11 или другую свободную пару.
2. Запустить симулятор на первом конце, PuTTY — на втором.
3. Повторить сценарии 1–13 кнопкой окна.
4. Сопоставить simulator.log с индикаторами.
5. Удерживать пробел: автоповтор не должен создавать дополнительные знаки.
6. При удержании увести фокус с окна: кнопка должна отпуститься.
7. Закрыть окно и запустить снова: COM-порт должен освобождаться.
8. Открыть занятый/несуществующий порт: должна появиться понятная ошибка.

Каждый конец пары открывает один процесс. Тестовый объект Python не заменяет эту проверку.

## Что ещё не проверено

- Загрузка и запуск новой прошивки на физическом SDK-1.1М.
- Сигналы USART6, реальные потери и интервалы.
- Обмен в обоих режимах через физический COM-порт.
- Связка симулятор–PuTTY через настоящую виртуальную COM-пару.
- Повторная генерация исходников через графический CubeMX: выполнена сборка подготовленных исходников.

Список COM-портов в рабочей среде был пуст. Эти проверки не заявляются пройденными. Для отчёта следует вписать реальные наблюдения после запуска; вымышленных результатов и скриншотов здесь нет.
