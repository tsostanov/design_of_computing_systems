# Проектирование вычислительных систем

Лабораторная работа №2 «Последовательный интерфейс UART», **вариант 3 — «Азбука Морзе»**.

Текущий проект `test_f427` переделан под ЛР №2. ЛР №1 сохранена в [коммите e7a9e48](https://github.com/tsostanov/design_of_computing_systems/tree/e7a9e4813b846f6feda4ed85eb60c893eca59def).

## Условие и реализация

Кнопка вводит точки и тире. После паузы программа расшифровывает букву A–Z и выводит в UART `received symbol: X`. Буквы, принятые через UART, сопровождаются сообщением `transmitting symbol: X` и проигрываются зелёным светодиодом. Приём, ввод кнопкой, отправка текста и мигание работают одновременно.

Символ `+` переключает UART между прерываниями и опросом. Ответ — `interrupts on` или `interrupts off`. Начальный режим — прерывания. Скорость — **115200 бит/с**.

Первая часть использует HAL UART в обоих режимах. Вторая часть выполнена **способом 2: Python-симулятор с виртуальным COM-портом**. Симуляция регистров и собственный UART-драйвер вместо HAL для второй части не требуются.

## Открытие, сборка и загрузка

1. Открыть STM32CubeIDE 1.9.0. Если проект уже открыт, выделить его и нажать **F5 / Refresh**.
2. В другом workspace: **File → Import → General → Existing Projects into Workspace**. Выбрать корень репозитория с `.project`, отметить `test_f427`, нажать Finish. Уже открытый проект повторно импортировать не нужно.
3. Выбрать конфигурацию **Debug**, затем **Project → Build Project**. При необходимости выполнить **Project → Clean** и снова собрать.
4. В Build Console проверить отсутствие ошибок. Результат: `Debug/test_f427.elf`; карта размещения: `Debug/test_f427.map`. Debug создаётся средой и не хранится в Git.
5. Подключить стенд по USB. Открыть **Run → Debug Configurations → STM32 C/C++ Application → test_f427 Debug**.
6. Использовать существующую настройку OpenOCD с `SDK1_1_M FTDBG.cfg`, подключающим `SDK11M_FT.cfg` и задающим JTAG. Эти файлы и карта памяти сохранены.
7. Нажать Debug. Если программа остановилась на `main`, нажать **Resume / F8**. Пока процессор остановлен отладчиком, обмен и мигание не работают.

`test_f427.ioc` содержит USART6 и NVIC. Исходники для сборки уже подготовлены: предварительно генерировать код не требуется. Пользовательские вызовы находятся в USER CODE или отдельных модулях. После самостоятельной регенерации CubeMX проверить, что USART6 инициализируется до `App_Init()`, а в цикле остаётся `App_Update()`. PC15 и PD13–PD15 не нужно назначать в CubeMX: их настраивает собственный драйвер.

## PuTTY и управление

1. В Диспетчере устройств найти COM-порт стенда: обычно **SDK 1.1M Debugger (Interface 1)** или **Dual RS232 (Interface 1)**. Номер COM зависит от компьютера. Interface 0 используется отладчиком.
2. В PuTTY выбрать **Connection type: Serial** и указать найденный порт.
3. **Connection → Serial**: Speed 115200, Data bits 8, Stop bits 1, Parity None, Flow control None.
4. **Terminal**: Local echo **Force off**, Local line editing **Force off**. Эхо выполняет стенд; отключение редактирования позволяет отправлять буквы сразу.
5. Открыть соединение и запустить прошивку.

При запуске выводится `interrupts on`. Если терминал открыт позже, начальное сообщение могло быть пропущено. Символ `+` всегда показывает новый фактический режим.

| Действие | Результат |
|---|---|
| Отправить `a` или `A` | Эхо исходного байта, `transmitting symbol: A`, зелёный: точка–тире |
| Кнопкой короткое, затем длинное нажатие; подождать | Жёлтое и красное подтверждение; `received symbol: A` |
| Отправить `+` | Эхо и смена режима, без добавления буквы |
| Нажать Enter | CR/LF возвращаются эхом; буква или ошибка не создаётся |
| Отправить `?`, цифру, пробел или другой неподдерживаемый байт | Эхо и `error: unsupported input` |

Поддерживаются **только латинские A–Z**, без цифр и русских букв. `transmitting symbol` означает принятие буквы: мигание начнётся, когда дойдёт очередь.

Служебные сообщения начинаются и заканчиваются CRLF. CR/LF терминала возвращаются как получены и могут визуально добавлять пустые строки, но не выполняют команд. Ввод кнопкой не проигрывается повторно зелёным: в ЛР №2 он расшифровывается и передаётся компьютеру.

| Проигрывание | **8 ожидающих букв + одна текущая** |

Удерживание кнопки не считается паузой. После девятого знака вся последовательность помечается переполненной и отвергается по окончании паузы. Интервалы вычисляются без `HAL_Delay`, разностью беззнаковых 32-битных счётчиков.

## Режимы и ошибки

**Прерывания:** HAL принимает/отправляет по байту через постоянные буферы. ISR перемещает байты и продолжает обмен; сообщения формирует основной цикл. Общие очереди защищены кратким маскированием только USART6_IRQn. SysTick продолжает работать.

**Опрос:** UART-источники прерываний и USART6_IRQn выключены. Нет данных — чтение возвращает `UART_NO_DATA`. При RXNE байт читается HAL с timeout=0. Передача обслуживается по TXE также с timeout=0.

Особенность этой HAL: `HAL_UART_Transmit(..., 1, 0)` может записать байт и вернуть HAL_TIMEOUT при ожидании TC. Проверка `TxXferCount` не даёт повторить уже записанный байт. Этот путь используется только в режиме опроса.

**Переключение:** текущий байт завершается; новые передачи кратко приостанавливаются, HAL-операции согласуются, меняется NVIC. Программные очереди, ввод кнопкой и анимация сохраняются. Уведомление выдаётся после переключения.

**Переполнение:** новая буква отклоняется с `error: letter queue full`. Когда TX не вмещает весь ответ, команда остаётся в RX; остальные процессы работают. При переполнении RX отбрасывается новый байт, сохраняются старые, выводится накопительный счётчик `error: uart rx_overflow=N line=N tx=N`. Повреждённые байты не передаются приложению, приём восстанавливается. Переполнение очереди результатов кнопки сообщается отдельно.

Буферы конечны. На одну букву отправляется длинный ответ, поэтому непрерывный поток может переполнить RX даже без переключения. Эхо потерянного байта не гарантируется. Потери под нагрузкой и длительность маскирования IRQ требуют проверки на стенде.

## Симулятор — Windows

Нужны Python с Tkinter и **пара виртуальных COM-портов**. Python сам не создаёт драйвер COM-портов. COM-порт физического стенда — это отдельный канал.

1. Создать пару, например **COM10 ↔ COM11**, установленной программой виртуальных портов. Вариант — [com0com](https://com0com.sourceforge.net/): открыть Setup, добавить пару, назначить свободные имена, применить и проверить порты в Диспетчере устройств. Нужна версия драйвера, совместимая с вашей Windows; изменение настроек безопасности ОС не входит в проект.
2. Из корня проекта выполнить в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r simulator/requirements.txt
.\.venv\Scripts\python.exe -m serial.tools.list_ports
.\.venv\Scripts\python.exe -m simulator --port COM10
```

3. Открыть **второй** конец, COM11, в PuTTY: 115200/8N1, flow control None, local echo и local line editing Force off.
4. Из PuTTY отправлять буквы и `+`. В окне удерживать кнопку мышью или пробелом. Длительность определяет точку/тире.
5. Наблюдать светодиоды, текущую букву, очередь и режим. Журнал переходов — `simulator.log` и консоль; другой файл задаётся через `--log путь.log`.

Каждый конец может открыть только один процесс. При ошибке открытия программа сообщает причину; при разрыве обмена окно показывает ошибку. Закрытие окна освобождает порт.

Режимы `interrupts on/off` здесь **логические**, не аппаратные прерывания ПК. Используется [pySerial](https://pyserial.readthedocs.io/en/stable/pyserial_api.html) с неблокирующим чтением и записью; неотправленный остаток сохраняется. Потеря фокуса отпускает кнопку, автоповтор пробела не создаёт новых нажатий.

Симулятор не заменяет испытания прошивки. Windows PuTTY не открывает Linux PTY внутри WSL как Windows COM-порт.

## Проверки

При доступном GCC для компьютера (например MinGW), из корня:

```powershell
python tests/run_tests.py
```

Если GCC не найден, задать полный путь в переменной `CC`. Стенд и pySerial не нужны: аппаратура C подменяется, транспорт Python проверяется тестовым объектом. Проверка окна требует Tkinter и явно пропускается без графической среды.

Выполнены:

- полная сборка Debug в STM32CubeIDE: **0 ошибок, 0 предупреждений**;
- 6 групп проверок настоящих C-модулей, включая UART с имитацией HAL;
- 11 Python-тестов: модель, окно, очередь, время, частичная запись и точное совпадение сообщений с C-приложением;
- запуск справки симулятора и проверка списка портов.

**На физическом стенде и через настоящую виртуальную COM-пару обмен пока не проверен:** подключённых портов не было. Сценарии и границы проверок: [docs/TESTING.md](docs/TESTING.md).
